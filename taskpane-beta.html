Before you consent

  • Roster, classifications, and the audit log stay in this tenant's Azure SQL. No copy is kept anywhere else.
  • Admin consent grants two application permissions, User.Read.All and GroupMember.Read.All, so recipients can be matched to the directory. Sign-in uses delegated User.Read. Mailbox contents are not read.
  • The audit log is append-only. The database denies updates and deletes on that table.
  • Send blocking works in New Outlook only after an administrator deploys the add-in in Integrated Apps. A sideloaded copy does not block a send. A first assignment in a tenant can take up to 72 hours.
  • Deleting this install's Azure resource group deletes the database and the add-in host.

Internal Domains

Recipients on these domains are treated as internal for clearance vetting. Directory membership alone isn't a reliable signal -- tenant guests (a gmail.com address, a partner domain) can legitimately be in the directory, so this list is the real internal/external boundary. Seeded from your signed-in domain on first load. Saved to the server so send-exceptions cannot be granted for internal addresses.

External Recipient Advisory

Shown as a confirmation the sender must acknowledge before the classification is inserted. Acknowledgment is audit-logged. Unknown recipients are blocked at send unless excepted or overridden — this advisory is not a send-anyway.

Send exceptions (external only)

Approved external addresses skip the “not on roster” send block. Internal unknown addresses must be imported into the directory — do not list them here. Pending rows are sender requests.

Unresolved clearance

Directory rows whose clearance is not a current ladder name. They are on the roster; /vet must not call them “not on the roster.” Fix the stored clearance. Standing exceptions do not apply.
